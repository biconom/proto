# CHANGELOG: 21 Августа 2026 (proto `v0.3.13` → `v0.3.15`)

Сводка изменений API после `v0.3.12`. Всё про экран «Стейкинг → Команда»:
**`Staking.RankProgress` дообогащён** карточками, счётчиками активированных
партнёров и возможностью открыть прогресс партнёра из своей команды.

Ломающих изменений на проводе нет. Единственная правка сигнатуры —
`GetRankProgress` принимает `Distributor.Id` вместо `Empty` (§4): пустой запрос по
проводу декодируется в значения по умолчанию, то есть в прежнее поведение
«показать себя». Перегенерировать клиент придётся, менять вызовы — нет.

## Что нужно сделать фронту — коротко

| Действие | Где подробно |

Ничего из существующего не удалено и не переименовано — только добавлено.

## 1. 👥 Карточки лидеров веток в `GetRankProgress`

**Проблема.** `RankProgress.legs` отдавал по ветке только `distributor_id`.
Чтобы показать список веток с логином и аватаром, фронту приходилось звать
`DistributorService` на каждую ветку — у крупного лидера это сотни запросов.

**Решение** — тот же BFF-приём, что в `Leaderboard` и `Geo.DistributorsInfo`:
плоские дедуплицированные справочники рядом с данными.

### `biconom/types/staking.proto`

```protobuf
message RankProgress {
    // ... существующие поля 1..10 не тронуты ...

    // Профили САМОГО партнёра и лидеров веток из `legs`.
    // Связь: `Leg.distributor_id == Distributor.id`.
    repeated biconom.types.Distributor distributors = 11;
    // Аккаунты-владельцы: связь `Distributor.account_id == Account.id`.
    // Внутри аккаунта — `User` с аватаром, статусом присутствия и контактами.
    repeated biconom.types.Account accounts = 12;
}
```

В `distributors` попадает **и сам партнёр**, чей прогресс запрошен, — под его
карточку в шапке экрана. Клиенту он и так известен, а вот админ спрашивает
прогресс по username, и без этого ему пришлось бы делать второй запрос ради
аватара и логина.

Как сопоставлять:

```
Leg.distributor_id → Distributor.id → Distributor.account_id → Account.id → Account.user
```

| Что | Где |
|---|---|
| Логин ветки | `Distributor.username` |
| Аватар | `Account.user.avatar` |
| Онлайн-статус | `Account.user.presence_status` |
| Контакты | `Account.user.email`, `Account.user.telegram_username` |

**Контакты заполняются**: в клиентском API ветки — это личники смотрящего, он и
так имеет право на их профиль; в админском доступ уже проверен правом
`ADMIN_STAKING`.

**Списки пусты, когда пуст `legs`** — то есть всегда внутри `GetState`: там блок
`rank` приходит без разбивки по веткам (её размер не ограничен).

Затронуты оба RPC: `client.staking.StakingService.GetRankProgress` и
`admin.staking.StakingAdminService.GetRankProgress`.

## 2. 📊 Счётчики партнёров, купивших депозит

**Проблема.** По ответу нельзя было сказать, сколько партнёров в структуре
реально участвуют в стейкинге: объёмы показывали деньги, а не людей.

### `biconom/types/staking.proto`

```protobuf
message RankProgress {
    // Сколько ЛИЧНИКОВ первой линии купили хотя бы один депозит.
    uint32 stakers_partners = 13;
    // То же по ВСЕЙ команде — поддерево целиком, без самого партнёра.
    uint32 stakers_team = 14;
}

message Leg {
    // Лидер ветки САМ активировал хотя бы один депозит.
    bool personal_activated = 8;
    // Сколько ЛИЧНИКОВ лидера ветки активировали депозит.
    uint32 stakers_partners = 9;
    // Сколько партнёров в КОМАНДЕ лидера ветки активировали депозит — всё его
    // поддерево, БЕЗ него самого.
    uint32 stakers_team = 10;
}
```

`personal_activated` — отдельный флаг, а не `stakers_partners > 0`: лидер может
не иметь ни одного депозита, но держать под собой активных партнёров, и наоборот.
Общее число активных в ветке = `stakers_team + personal_activated`.

Правила, которые важно понимать при вёрстке:

| Правило | Следствие для экрана |
|---|---|
| Считаются **партнёры**, а не депозиты | второй депозит того же человека счётчик не двигает |
| Учёт **за всё время** | созревание, `ClaimDeposit` и закрытие депозита партнёра из счёта не убирают — величина только растёт, как `personal_volume` |
| `stakers_team` — поддерево **без самого партнёра** | у партнёра без структуры это `0`, даже если у него самого есть депозиты |
| `Leg.stakers_team` — тоже **без лидера ветки** | активные в ветке целиком = `Leg.stakers_team + Leg.personal_activated` |
| Лимит на ветку на счётчик **не влияет** | это метрика структуры, а не денег: `capped` её не режет |

`RankProgress.stakers_partners` и `RankProgress.stakers_team` читаются за `O(1)`,
поэтому приходят **и в `GetState`** (в блоке `rank`), а не только в
`GetRankProgress`. Поля внутри `Leg` — только там, где есть сам `legs`.

## 3. 🧩 Сборка экрана «Стейкинг → Команда»

Один вызов `GetRankProgress` закрывает весь экран — второго запроса не нужно.

### Шапка — карточка самого партнёра

| Элемент | Откуда |
|---|---|
| Аватар, логин, ID | `distributors` / `accounts` по `distributor_id` (см. §4) |
| Бейдж «человек» — личники | `stakers_partners` |
| Бейдж «группа» — команда | `stakers_team` |
| Личный объем | `personal_volume` |
| Лимит объема с ветки | `next.max_per_leg` |
| Учитываемый объем с веток | `team_volume − personal_volume` |
| Итоговый командный объем | `team_volume` |

Оба «объёмных» поля считаются под **следующий** ранг, потому что лимит на ветку
зависит от проверяемого ранга. На максимальном ранге `next` и `team_volume`
отсутствуют — блок лимита показывать нечему.

### Цифры по депозитам показываемого партнёра — блок `summary`

| Элемент | Откуда |
|---|---|
| Личных инвестиций за всё время | `summary.invested_total` |
| Активных депозитов: сколько / на сумму | `summary.active_count` / `summary.active_total` |
| Текущая ставка тира | `summary.current_rate` (прятать по `active_count == 0`, см. §5) |
| Депозитов за всё время | `summary.total_count` |
| Начислено дохода / из него в реинвест | `summary.total_income_paid` / `summary.total_reinvested` |
| Созрело и ждёт решения: сколько / на сумму | `summary.matured_count` / `summary.matured_total` |
| Личный вклад для рангов | `summary.personal_volume` (то же, что `personal_volume`) |

Разница `personal_volume − invested_total` показывает, сколько объёма создано
реинвестом, а не новыми деньгами. Созревшие депозиты в `active_total` НЕ входят —
они больше не зарабатывают; отсюда типичная картина «`active_total` ноль,
`matured_total` не ноль, `current_rate` = `"0.00"`».

### Прогресс к следующему рангу

| Элемент | Откуда |
|---|---|
| Текущий ранг и дата | `current_rank`, `achieved_at` |
| Какой ранг следующий и его ставка | `next.rank`, `next.referral_rate` |
| Сколько нужно вклада / оборота | `next.required_personal_volume` / `next.required_team_volume` |
| Бонус за достижение | `next.achievement_bonus` (нет у рангов 1..3) |
| Полный оборот команды без лимитов | `team_volume_uncapped` |
| История взятых рангов | `achievements[]` |

`team_volume_uncapped − team_volume` — это ровно то, что срезал лимит на ветку, и
прямой ответ на «у меня в команде $60 000, почему не дали ранг, где нужно
$50 000».

### Список «Мои ветки» — по элементу на `legs[]`

| Элемент | Откуда |
|---|---|
| Аватар, логин, ID | `distributors` / `accounts` по `Leg.distributor_id` |
| Бейдж «человек» — личники лидера ветки | `Leg.stakers_partners` |
| Бейдж «группа» — команда лидера ветки | `Leg.stakers_team` |
| Личный объем | `Leg.leader_personal_volume` |
| Командный объем | `Leg.branch_volume` |
| Учитываемый объем | `Leg.counted` |
| Отметка «сам активировал» | `Leg.personal_activated` |
| Ветка обрезана лимитом | `Leg.capped` |
| Засчитан только вклад лидера | `Leg.leader_exceeds_cap` |

## 4. 👁 Просмотр прогресса партнёра из своей команды (v0.3.14)

**Задача.** Экран строится не только для себя: из списка веток нужно провалиться
в карточку партнёра и увидеть его квалификацию.

### `biconom/client/staking/staking.proto`

```protobuf
rpc GetRankProgress(biconom.types.Distributor.Id) returns (biconom.types.Staking.RankProgress);
```

Запрос — **общая модель идентификатора**, без сообщения-обёртки: тем же приёмом
адресуется депозит в `GetDeposit` / `ClaimDeposit`, и так же устроен админский
`GetRankProgress`. Спросить можно и по числовому id (так фронт проваливается из
списка веток), и по username.

Было `GetRankProgress(google.protobuf.Empty)`. **Прежнее поведение сохранено**:
пустой `identifier` = свой прогресс.

### Правила доступа

| Кого спрашиваем | Ответ |
|---|---|
| Себя (`identifier` не задан или свой id) | прогресс отдаётся всегда |
| Партнёра из своей команды | отдаётся |
| Постороннего | `PermissionDenied`, `DISTRIBUTOR_VIEW_PERMISSION_DENIED` |
| Несуществующего id / username | `NotFound`, `DISTRIBUTOR_NOT_FOUND` |

Гейт — **тот же, что у `DistributorService.Get`**: свой профиль, команда по
спонсорскому дереву, слотовая иерархия, плюс глобальный просмотр у поддержки.
Отдельного правила для стейкинга нет намеренно — иначе видимость структуры
разъехалась бы между экранами. Вышестоящий (свой спонсор) под правило не
подпадает: смотреть можно вниз, не вверх.

### `biconom/types/staking.proto`

```protobuf
message RankProgress {
    // ЧЕЙ это прогресс — ключ к карточке в шапке экрана.
    uint32 distributor_id = 15;
    // Агрегаты по депозитам ПОКАЗЫВАЕМОГО партнёра (та же модель, что
    // `State.summary`). Приходит только в `GetRankProgress`.
    DepositsSummary summary = 16;
}
```

`summary` — то, без чего чужую карточку не собрать: `State` всегда про себя, и
когда смотришь партнёра из команды, его цифры взять больше неоткуда.

| Метрика | Поле |
|---|---|
| Личных инвестиций за всё время | `summary.invested_total` |
| Активных депозитов сейчас / на сумму | `summary.active_count` / `summary.active_total` |
| Текущая ставка тира | `summary.current_rate` |
| Депозитов за всё время | `summary.total_count` |
| Начислено дохода / из него в реинвест | `summary.total_income_paid` / `summary.total_reinvested` |
| Созрело и ждёт решения | `summary.matured_count` / `summary.matured_total` |
| Личный вклад для рангов | `summary.personal_volume` (= `RankProgress.personal_volume`) |

Внутри `State` поле **не заполняется**: та же сводка уже лежит на верхнем уровне
ответа, и держать её в блоке ранга вторым экземпляром незачем.

Появляется во ВСЕХ ответах, включая `GetState` и админский `GetRankProgress`. По
нему в `distributors` / `accounts` находятся логин, аватар и контакты
показываемого партнёра — сами данные не дублируются, чтобы два представления
одного факта не разъехались.

`relationship_state` внутри карточек по-прежнему считается от **смотрящего**:
«кем этот человек приходится мне», а не показываемому партнёру.

## 5. 🔢 `DepositsSummary.current_rate` больше не бывает пустым (v0.3.15)

**Было:** пустая строка, когда активных депозитов нет.
**Стало:** всегда коэффициент строкой, в том числе `"0.00"`.

Причина — пустая строка склеивала два разных состояния. `tier_rate` даёт ноль и
когда активных депозитов нет, и когда они есть, но их суммы не хватает даже на
нижнюю ступень сетки; во втором случае ставка **реально нулевая**, выплата
посчиталась бы как 0, и «не определена» было бы неверно.

Плюс тип: все остальные ставки в API — непустые строки, и `parseFloat("")` даёт
`NaN`. Теперь поле парсится одинаково во всех случаях.

**Что делать фронту:** решение «показывать блок ставки или нет» принимать по
`active_count == 0`, а не по пустоте `current_rate`. Если раньше была проверка
`current_rate === ""` — заменить на `active_count === 0`.

## 6. ⚠️ Три вещи, на которых легко ошибиться при вёрстке

### 6.1. `legs` содержит ВСЮ первую линию, включая пустые ветки

Сервер возвращает по элементу на каждого лично приглашённого партнёра — в том
числе тех, у кого всё по нулям (`branch_volume = "0.000000"`, `counted =
"0.000000"`, `stakers_team = 0`, `personal_activated = false`). У партнёра с
сотнями личников это сотни элементов и, соответственно, сотни карточек в
`distributors` / `accounts`.

Показывать в списке «Мои ветки» имеет смысл только значимые. Практичный фильтр:

```
branch_volume != "0.000000" || stakers_team > 0 || personal_activated
```

`legs_count` считает ВСЕ ветки, независимо от фильтра, — им и подписывайте
«всего веток», иначе цифра разойдётся с длиной отфильтрованного списка.

Серверная фильтрация не сделана намеренно: порог «что считать значимым» —
продуктовое решение, и зашивать его в контракт до согласования не стали. Если
размер ответа окажется проблемой — скажите, добавим параметр.

### 6.2. `counted` может быть БОЛЬШЕ, чем `max_per_leg`

Выглядит как ошибка, но это правило программы. Когда **личный вклад лидера
ветки** превышает лимит, засчитывается весь его вклад целиком, а нижестоящие этой
ветки не учитываются вовсе. Признак — `leader_exceeds_cap = true` (при этом
`capped = false`, потому что обрезки не было).

Реальный пример из ответа staging:

| Поле | Значение |
|---|---|
| `max_per_leg` | `85000.000000` |
| `leader_personal_volume` | `268827.968320` |
| `branch_volume` | `1247536.292287` |
| `counted` | `268827.968320` ← весь вклад лидера |
| `capped` | `false` |
| `leader_exceeds_cap` | `true` |

Нижестоящие этой ветки ($978 708) не засчитаны вовсе. Три состояния ветки, которые
стоит показывать по-разному:

| `capped` | `leader_exceeds_cap` | Что произошло |
|---|---|---|
| `false` | `false` | ветка засчитана целиком, лимит не сработал |
| `true` | `false` | ветка обрезана до `max_per_leg` |
| `false` | `true` | засчитан весь вклад лидера, его структура не учтена |

### 6.3. На максимальном ранге половины полей нет

При `is_max = true` отсутствуют `next` и `team_volume` — проверять по рангу
больше нечего. `team_volume_uncapped`, `legs`, счётчики и `summary` приходят как
обычно. Блок «до следующего ранга» в этом случае не рисуется вовсе.

## 7. 📐 Форматы значений

| Тип | Как выглядит | Как читать |
|---|---|---|
| Деньги | `"1200.000000"` | строка, знаков после точки = `precision` валюты (USDT — 6). Не парсить в `double` для арифметики |
| Ставки | `"0.05"`, `"0.16"`, `"0.00"` | **коэффициент**, не процент. Процент = × 100. Умножать напрямую: `выплата = тело × rate` |
| Отсутствующее значение | поля нет в JSON (`optional`) | содержательно отличается от нуля: у ранга 1 нет требования по обороту, у рангов 1..3 — бонуса за достижение |
| Даты | RFC 3339 (`"2026-08-21T09:25:04Z"`) | у выплат это ПЛАНОВЫЙ момент цикла, не момент обработки |

## 8. 🚦 Ошибки `GetRankProgress`

| Ситуация | Код | Строка |
|---|---|---|
| Нет права видеть профиль запрошенного | `PermissionDenied` | `DISTRIBUTOR_VIEW_PERMISSION_DENIED` |
| Запрошенного дистрибьютора не существует | `NotFound` | `DISTRIBUTOR_NOT_FOUND` |
| Токен не Session (гость) | `Unauthenticated` | `GUEST_ACCESS_DENIED` |
| Нет права `STAKING_USE` / нет привязки к дистрибьютору | `PermissionDenied` | `ACCESS_SCOPE_DENIED` |

Свой прогресс (пустой идентификатор) ошибок доступа не даёт никогда.
