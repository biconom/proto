# 2026-11-04 — proto 0.3.36–0.3.38 (core 1.10.52–1.10.55)

## «Мои линии»: глубина выплат, награда и свежие новички — в `GetSlotV2`

`biconom.types.MarketingSlotV2` (ответ `MarketingService/GetSlotV2`):

| Поле | Что значит |
|---|---|
| `uint32 payout_depth_max = 11` | до какого уровня включительно владелец view-слота сейчас получает награды (1..7) |
| `uint32 qualified_first_line_count = 12` | активные личники владельца в этом дереве; `payout_depth_max = min(count + 1, 7)` |
| `LevelState.repeated Price rewards = 7` | награда за одного партнёра уровня за активацию его ваучера (из плана дерева) |
| `LevelState.repeated uint32 recent_slot_ids = 8` | первые 3 слота уровня в том же порядке, что `ListLevelSlots` (свежая первая активация лицензии выше, без активации — в конце) |

Уровень с `level > payout_depth_max` — «не зарабатывает» (перечёркнутая иконка).
«Заработано» на таком уровне может быть ненулевым: это доход прошлых периодов.

Подробности слотов из `recent_slot_ids` — в `slots`, их дистрибьюторы — в `distributors`,
аккаунты (аватар, имя) — в `accounts`. Списки дедуплицированы; **ищите по id**, не по
позиции: раньше там было ровно два элемента (executor и view), теперь больше.
`slot_states` и `distributor_states` по-прежнему только для executor и view.

## Шапка «Спонсоры» — в том же `GetSlotV2`

| Поле | Что значит |
|---|---|
| `repeated uint32 upline_slot_ids = 13` | до 3 вышестоящих view-слота на пути к слоту executor (включительно), ближайшие первыми |
| `uint32 upline_count = 14` | сколько всего слотов на этом пути (= разница уровней) |

- Левый блок — `upline_slot_ids[0]` (прямой вышестоящий).
- Правый блок — аватары `upline_slot_ids`, «+N» = `upline_count − upline_slot_ids.len()`.
- Выше своего слота цепочка не идёт. При просмотре своего слота или слота не из своей
  структуры оба поля пустые. Подробности слотов — в `slots` / `distributors` / `accounts`.

## Экран «цепочка до слота» (Below you) — уже есть, `GetSlotBreadcrumbs`

Новый метод не нужен: экран со списком «You → промежуточные слоты → Target slot»
строится на существующем `MarketingService/GetSlotBreadcrumbs` (запрос — тот же
`biconom.types.Slot.Id`, что у `GetSlotV2`, например `{"id": <slot_id>}`).

- **Права.** Слот должен быть в вашей слотовой структуре (ниже вашего слота в том же
  дереве), иначе ошибка `SLOT_VIEW_PERMISSION_DENIED`. Дерево берётся у запрошенного
  слота, ваш слот ищется в нём же.
- **Строки сверху вниз** — `chain_ids`: `[0]` — ваш слот («You»), последний — запрошенный
  («Target slot»), между ними все промежуточные, без ограничения по количеству. Свой слот
  запросили — в списке ровно один элемент.
- **Данные строки** — как везде, по id: `slots[]` (по `chain_ids`) → `slots[].distributor_id`
  → `distributors[]` → `distributors[].account_id` → `accounts[]` (имя, аватар). Списки
  дедуплицированы: у одного дистрибьютора может быть несколько слотов в цепочке —
  запись дистрибьютора придёт одна, ищите по id, не по позиции.
- **Метка справа** — `distributors[].relationship_state`: **реферальная** связь владельца
  слота с вами (не слотовая; слотовая — в `slots[].relationship_state`, для этого экрана
  не нужна).

| `relationship_state.kind` | `level_diff` | Метка |
|---|---|---|
| `PERSONAL` | — | You (ваш же слот) |
| `TEAM` | 1 | First Line |
| `TEAM` | N ≥ 2 | Team: N line |
| `UPLINE` / `NONE` | — | Not in team |

## Экран линии (нажатие на уровень) — новый `MarketingService/ListLevelSlots` (proto 0.3.37, core 1.10.53)

Список слотов одного уровня глубины под просматриваемым слотом, с пагинацией. Уровень —
любой (≥ 1), ограничения 7 нет. Права — те же, что у `GetSlotV2`.

Запрос `ListLevelSlotsRequest`:

| Поле | Что значит |
|---|---|
| `optional Slot.Id slot_id = 1` | просматриваемый слот (не указан — слот по умолчанию, как у `GetSlotV2`) |
| `uint32 level = 2` | уровень под ним: 1 — первая линия; 0 — ошибка `SLOT_LEVEL_INVALID` |
| `optional Slot.Id cursor = 3` | последний слот предыдущей страницы; не указан — первая страница |
| `optional uint32 limit = 4` | размер страницы 1..100; не указан, 0 или больше 100 — 100 |

Ответ `ListLevelSlotsResponse`: `slot_ids` (страница), `total_count` (всего на уровне),
`has_more` (есть следующая страница), `view_slot_id` + справочники `slots` / `distributors` /
`accounts` (в них и view-слот — его владелец в шапке «PartnerLogin • N line»).

- **Порядок всегда один** и тот же, что у `GetSlotV2.levels_state[].recent_slot_ids`:
  по дате первой активации лицензии, свежие первыми; равная дата — больший slot_id выше;
  слоты без единой активации — в конце. Топ-3 на экране линий = первые 3 первой страницы.
- **Следующая страница:** `cursor = {"id": <последний из slot_ids>}`, пока `has_more = true`.
  Курсор должен стоять ровно на этом уровне под просматриваемым слотом, иначе
  `SLOT_CURSOR_INVALID`; несуществующий — `SLOT_CURSOR_NOT_FOUND`.
- **Метка справа** — как в `GetSlotBreadcrumbs`: `distributors[].relationship_state` —
  реферальная связь с вами (`TEAM` + 1 — First Line, `TEAM` + N — Team: N line,
  `UPLINE` / `NONE` — Not in team, `PERSONAL` — вы).

## Экран «Find a Partner» — уже есть, `MarketingService/SearchSlots`

Новый метод не нужен. Поиск слотов по логину владельца в конкретном дереве, только в
вашей слотовой структуре:

```json
{
  "usernamePrefix": "John-Smith",
  "treeIds": [1],
  "filterSlotRelationshipStateKinds": ["TEAM"],
  "limit": 20
}
```

| Поле | Что значит |
|---|---|
| `username_prefix` | начало логина дистрибьютора-владельца слота (пробелы по краям обрезаются; пустой — ошибка `DISTRIBUTOR_USERNAME_EMPTY`) |
| `tree_ids` | только слоты указанных деревьев |
| `filter_slot_relationship_state_kinds: [TEAM]` | только слоты НИЖЕ вашего слота по слотовому дереву; добавьте `PERSONAL`, чтобы в выдаче были и ваши слоты |
| `limit` | по умолчанию 10, максимум 1000 |

Ответ: `slots`, `slot_states`, `distributors`, `accounts` (имя, ID, аватар) — сопоставлять
по id, как везде.

- **Метка справа** — `distributors[].relationship_state` (реферальная связь с вами):
  `UPLINE` + `level_diff` 1 — Sponsor, `TEAM` + 1 — First Line, `TEAM` + N — Team: N line,
  `NONE` — Not in team, `PERSONAL` — вы.
- **`x-act-as` — любой ваш контекст** (core 1.10.53). Слотовая связь считается от вашего
  слота в дереве найденного слота: если в `x-act-as` слот этого дерева — от него; если
  дистрибьютор или слот другого дерева (например, Pro при поиске в Lite) — сервер сам
  берёт ваш последний слот в этом дереве. Нет вашего слота в дереве — `TEAM` там пусто.
- В выдаче только слоты с лицензией `Active` или `Inactive`; `Expired` / `Suspended`
  не находятся.
- Пагинации и своей сортировки нет: порядок — по логину, первые `limit` совпадений.

## Быстрый старт: окно от кнопки «Начать» — `QuickStartService/Start` (proto 0.3.38, core 1.10.55)

24 часа теперь отсчитываются **от нажатия «Начать»**, а не от регистрации. Начать может
любой пользователь, в том числе давно зарегистрированный. Нажатие — одно за всё время:
окно не продлевается и не перезапускается.

| Изменение | Что делать фронту |
|---|---|
| `rpc Start(google.protobuf.Empty) returns QuickStart.State` | вызвать по кнопке «Начать»; ответ — уже обновлённое состояние |
| `State.Status STATUS_NOT_STARTED = 5` | показать кнопку «Начать» и список задач (статусы по графу: `ACTIVE` / `LOCKED`, `COMPLETED` — если уже закрыты), без таймера |
| `State.started_at = 7` | начало окна; пусто до старта |
| `State.duration_secs = 8` | длина окна в секундах (86400) — для текста «24 часа» до старта |
| `State.deadline_at` | конец окна = `started_at + duration_secs`; пусто до старта |

Повторный `Start` безопасен: ничего не меняет, возвращает текущее состояние.
`CheckTelegramMembership` до старта отвечает `QUICK_START_NOT_ACTIVE`.

**Условия — по текущему состоянию, а не по событиям окна.** Telegram, привязанный
раньше, давняя аватарка, давние личники (`TaskProgress.progress` у
`CONDITION_KIND_REFERRAL` — все прямые личники) и подписки на чаты, сделанные до
старта, засчитываются. Сразу после `Start` сервер сам засчитывает выполненное и
проверяет членство в чатах; награды приходят по цепочке задач (задача открывается,
когда закрыт её родитель), уведомлениями. Фронт после `Start` опрашивает `Get`
несколько секунд, пока карточки не обновятся.

**Засчитано ≠ выплачено.** Выполненное условие фиксируется сразу (`STATUS_FULFILLED`),
но награда приходит только когда задача открыта — закрыт её родитель по графу
(`parent_id`). Как только родитель закрыт, открывшаяся задача с уже выполненным
условием закрывается в тот же момент (`STATUS_COMPLETED` + награда), и так по цепочке
вниз до первой невыполненной задачи. Пример — давний пользователь, у которого всё
уже есть (цепочка Telegram → канал → группа → аватарка → личник):

| Момент | Статусы | Награда |
|---|---|---|
| нажал «Начать» | Telegram `COMPLETED`; группа, аватарка, личник `FULFILLED` (ждут канал) | 2000 за Telegram |
| сервер нашёл подписку на канал (секунды после старта) | канал → группа → аватарка → личник `COMPLETED` каскадом | 4 × 2000 + финальный бонус 10 000 |

До «Начать» ничего не засчитывается и не запоминается. Если окно истекло, а задача
так и осталась закрыта родителем, — награды за неё нет (`STATUS_EXPIRED`), даже если
условие было выполнено.

Пользователи, получившие награды до этой версии (окно тогда шло от регистрации),
видят `STATUS_NOT_STARTED` с уже закрытыми задачами и продолжают после «Начать».

Сценарий:

```
Get            → status NOT_STARTED, duration_secs 86400, tasks[…]
Start          → status ACTIVE, started_at T, deadline_at T+24h
(через 1–5 с)
Get            → telegram_connect COMPLETED, telegram_channel COMPLETED, …
```

На проде кнопка заработает, когда сервер переключат на `start_mode: button` — это
делается вместе с выпуском фронта; до этого `Start` возвращает состояние без изменений,
а окно идёт от регистрации, как сейчас.
