# CHANGELOG: 22 Августа 2026 (proto `v0.3.15` → `v0.3.17`)

Одно добавление: **`DistributorService.GetBreadcrumbs`** — навигационная цепочка
«хлебные крошки» от авторизованного дистрибьютора вниз до указанного, со всеми
промежуточными звеньями и готовыми справочниками для отрисовки.

Ломающих изменений нет: существующие методы и сообщения не тронуты, ничего не
переименовано и не удалено. Достаточно перегенерировать клиент.

## Что нужно сделать фронту — коротко

| Действие | Где подробно |
|---|---|
| Перегенерировать клиент из `.proto` | — |
| Заменить самосбор пути из `ListPartners.upline_ids` на один `GetBreadcrumbs` | §2 |
| Рисовать строку навигации по `chain_ids` (порядок уже готовый) | §3 |
| Обработать `PermissionDenied` при провале по чужой ссылке | §4 |

---

## 1. 🧭 Зачем метод

**Проблема.** При провале вглубь структуры (`ListPartners` → партнёр → его
партнёр → …) фронту нужна строка «Я / Партнёр А / Партнёр Б / Целевой», чтобы
вернуться на любой уровень. Собрать её было нечем:

- `ListPartners.upline_ids` даёт вышестоящих **целевого** — линию до корня сети,
  а не отрезок «от меня до целевого», и её ещё надо резать по `executor`;
- при переходе по прямой ссылке (`/distributor/12345`) промежуточных звеньев на
  клиенте вообще нет — их пришлось бы добирать поштучно через `Get`;
- в каждой карточке нужны логин и аватар, то есть ещё по запросу на звено.

**Решение.** Один вызов отдаёт готовый упорядоченный путь плюс плоские
дедуплицированные справочники — тем же BFF-приёмом, что `ListPartners` и
`Staking.RankProgress`.

## 2. 📜 Контракт

### `biconom/client/distributor/distributor.proto`

```protobuf
service DistributorService {
    // ... существующие RPC не тронуты ...

    rpc GetBreadcrumbs(biconom.types.Distributor.Id) returns (GetBreadcrumbsResponse);
}

message GetBreadcrumbsResponse {
    // ID дистрибьютора, который выполняет запрос (авторизованный пользователь).
    uint32 executor_distributor_id = 1;
    // ID запрошенного дистрибьютора — хвост цепочки.
    uint32 view_distributor_id = 2;
    // Цепочка сверху вниз.
    repeated uint32 chain_ids = 3;
    // Дедуплицированные дистрибьюторы всех звеньев цепочки.
    repeated biconom.types.Distributor distributors = 4;
    // Дедуплицированные аккаунты-владельцы звеньев.
    repeated biconom.types.Account accounts = 5;
}
```

Запрос — **общая модель идентификатора** без сообщения-обёртки: тем же приёмом
устроены `DistributorService.Get` и `StakingService.GetRankProgress`. Спросить
можно и по числовому `id` (так фронт проваливается из списка партнёров), и по
`username` (так открывается прямая ссылка).

**Пустой `identifier` = «мои крошки»**: целевым считается сам авторизованный, и
`chain_ids` содержит ровно один элемент. Ошибки это не даёт.

## 3. 🧩 Как рисовать

`chain_ids` приходит **уже в порядке отрисовки** — слева направо:

```
chain_ids[0] = executor_distributor_id   ← «Я», самый левый элемент
...                                        промежуточные звенья, сверху вниз
chain_ids[last] = view_distributor_id    ← текущая позиция, самый правый
```

Сортировать и разворачивать на клиенте ничего не нужно. Каждый элемент — кликабельный
переход на `ListPartners(parent_id = chain_ids[i])`.

Как сопоставлять данные звена:

```
chain_ids[i] → Distributor.id → Distributor.account_id → Account.id → Account.user
```

| Что показать | Откуда |
|---|---|
| Логин звена | `Distributor.username` |
| Аватар | `Account.user.avatar` |
| Онлайн-статус | `Account.user.presence_status` |
| Контакты | `Account.user.email`, `Account.user.telegram_username` |
| Кем звено приходится мне | `Distributor.relationship_state` |

`relationship_state` считается **от смотрящего**: у первого элемента это
`PERSONAL`, у остальных — `TEAM` с `level_diff`, равным глубине от меня. По нему
же удобно подписывать уровень под каждой крошкой.

**Контакты заполняются** — все звенья цепочки по определению внутри моей
структуры, право на их профиль у меня уже есть (тот же принцип, что в
`DistributorService.Get`).

Длина цепочки = глубина целевого относительно меня + 1. Сворачивание длинной
строки («Я / … / Партнёр Б / Целевой») — на стороне клиента: серверного лимита
намеренно нет, аватар в ответе — это метаданные `Image`, а не файл.

## 4. 👁 Правила доступа

Метод отвечает на вопрос «как пройти от меня до этого человека», поэтому доступ
строже, чем у `Get`: путь существует только **вниз**.

| Кого спрашиваем | Ответ |
|---|---|
| Себя (пустой `identifier` или свой id) | цепочка из одного элемента |
| Партнёра из своей команды (любой глубины) | полная цепочка от меня до него |
| Своего спонсора / соседнюю ветку / чужую сеть | `PermissionDenied` |
| Несуществующего id или username | `NotFound` |

Глобальное право просмотра (админ/поддержка) на это правило **не влияет**: оно
даёт видеть чужой профиль, но не создаёт пути к нему. Для целевого вне своей
структуры такой смотрящий получает тот же `PermissionDenied`.

Инвариант, на который можно опираться безусловно: `chain_ids[0]` **всегда** равен
`executor_distributor_id`, `chain_ids[last]` — `view_distributor_id`. Звеньев выше
запрашивающего в цепочке не бывает.

### Ошибки

| Ситуация | Код | Строка |
|---|---|---|
| Целевой вне моей структуры | `PermissionDenied` | `DISTRIBUTOR_VIEW_PERMISSION_DENIED` |
| Целевого не существует | `NotFound` | `DISTRIBUTOR_VIEW_NOT_FOUND` |
| Сессия не привязана к дистрибьютору | `NotFound` | `DISTRIBUTOR_NOT_FOUND` |
| Токен не Session (гость) | `Unauthenticated` | `GUEST_ACCESS_DENIED` |
| Скоуп токена — подтверждение | `PermissionDenied` | `ACCESS_SCOPE_DENIED` |

Гостевого доступа у метода нет намеренно: крошки — это положение относительно
конкретного смотрящего, вне сессии они не определены.

## 5. 🩹 Правка `v0.3.17` — цепочка больше не уходит выше запрашивающего

Только для тех, кто успел посмотреть `v0.3.16` на staging. Поведения, описанного
выше, оно не меняет — оно приводит реализацию к нему.

**Было (`v0.3.16`, ошибка).** Для смотрящего с глобальным правом просмотра, у
которого своей цепочки к целевому нет, метод отдавал вышестоящую линию целевого
до корня сети. Запрос дистрибьютора `406` из-под дистрибьютора `4` (соседняя
ветка) возвращал `chain_ids = [1, 2, 9, 58, 406]` — ни одного звена из структуры
запрашивающего, зато его собственный спонсор `1` в списке.

**Стало (`v0.3.17`).** Такой ответ невозможен: нет пути вниз — `PermissionDenied`.
Ветка «вышестоящая линия для глобального просмотра» убрана целиком.

Отличить старое поведение от нового на клиенте можно было бы по
`chain_ids[0] != executor_distributor_id`, но проверка не нужна — в `v0.3.17`
это условие не выполняется никогда.
