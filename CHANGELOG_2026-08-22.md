# CHANGELOG: 22 Августа 2026 (proto `v0.3.15` → `v0.3.20`)

Три добавления — «хлебные крошки» для обеих иерархий, устроенные одинаково, плюс
последние личники прямо в ответе главного экрана:

- **`DistributorService.GetBreadcrumbs`** (§1–§5) — цепочка по **реферальному**
  дереву от авторизованного дистрибьютора вниз до указанного.
- **`MarketingService.GetSlotBreadcrumbs`** (§6) — цепочка по **маркетинговому**
  дереву от активного слота запрашивающего вниз до указанного слота.
- **`AccountService.GetCurrent` → `last_partner_distributors`** (§7) — три последних
  лично приглашённых партнёра с готовыми аккаунтами и профилями, в корне ответа.

Оба отдают готовый к отрисовке порядок `chain_ids` плюс плоские дедуплицированные
справочники, так что второго запроса на сборку строки навигации не нужно.

Ломающих изменений нет: существующие методы и сообщения не тронуты, ничего не
переименовано и не удалено. Достаточно перегенерировать клиент.

## 1. 🧭 Зачем `GetBreadcrumbs`

**Проблема.** При провале вглубь структуры (`ListPartners` → партнёр → его
партнёр → …) фронту нужна строка «Я / Партнёр А / Партнёр Б / Целевой», чтобы
вернуться на любой уровень. Собрать её было нечем:

- `ListPartners.upline_ids` даёт вышестоящих **целевого** — линию до корня сети,
  а не отрезок «от меня до целевого», и её ещё надо резать по `executor`;
- при переходе по прямой ссылке (`/distributor/12345`) промежуточных звеньев на
  клиенте вообще нет — их пришлось бы добирать поштучно через `Get`;
- в каждой карточке нужны логин и аватар, то есть ещё по запросу на звено.

**Решение.** Один вызов отдаёт готовый упорядоченный путь плюс плоские
дедуплицированные справочники — тем же BFF-приёмом, что `ListPartners` и
`Staking.RankProgress`.

## 2. 📜 Контракт `GetBreadcrumbs`

### `biconom/client/distributor/distributor.proto`

```protobuf
service DistributorService {
    // ... существующие RPC не тронуты ...

    rpc GetBreadcrumbs(biconom.types.Distributor.Id) returns (GetBreadcrumbsResponse);
}

message GetBreadcrumbsResponse {
    // ID дистрибьютора, который выполняет запрос (авторизованный пользователь).
    uint32 executor_distributor_id = 1;
    // ID запрошенного дистрибьютора — хвост цепочки.
    uint32 view_distributor_id = 2;
    // Цепочка сверху вниз.
    repeated uint32 chain_ids = 3;
    // Дедуплицированные дистрибьюторы всех звеньев цепочки.
    repeated biconom.types.Distributor distributors = 4;
    // Дедуплицированные аккаунты-владельцы звеньев.
    repeated biconom.types.Account accounts = 5;
}
```

Запрос — **общая модель идентификатора** без сообщения-обёртки: тем же приёмом
устроены `DistributorService.Get` и `StakingService.GetRankProgress`. Спросить
можно и по числовому `id` (так фронт проваливается из списка партнёров), и по
`username` (так открывается прямая ссылка).

**Пустой `identifier` = «мои крошки»**: целевым считается сам авторизованный, и
`chain_ids` содержит ровно один элемент. Ошибки это не даёт.

## 3. 🧩 Как рисовать `GetBreadcrumbs`

`chain_ids` приходит **уже в порядке отрисовки** — слева направо:

```
chain_ids[0] = executor_distributor_id   ← «Я», самый левый элемент
...                                        промежуточные звенья, сверху вниз
chain_ids[last] = view_distributor_id    ← текущая позиция, самый правый
```

Сортировать и разворачивать на клиенте ничего не нужно. Каждый элемент — кликабельный
переход на `ListPartners(parent_id = chain_ids[i])`.

Как сопоставлять данные звена:

```
chain_ids[i] → Distributor.id → Distributor.account_id → Account.id → Account.user
```

| Что показать | Откуда |
|---|---|
| Логин звена | `Distributor.username` |
| Аватар | `Account.user.avatar` |
| Онлайн-статус | `Account.user.presence_status` |
| Контакты | `Account.user.email`, `Account.user.telegram_username` |
| Кем звено приходится мне | `Distributor.relationship_state` |

`relationship_state` считается **от смотрящего**: у первого элемента это
`PERSONAL`, у остальных — `TEAM` с `level_diff`, равным глубине от меня. По нему
же удобно подписывать уровень под каждой крошкой.

**Контакты заполняются** — все звенья цепочки по определению внутри моей
структуры, право на их профиль у меня уже есть (тот же принцип, что в
`DistributorService.Get`).

Длина цепочки = глубина целевого относительно меня + 1. Сворачивание длинной
строки («Я / … / Партнёр Б / Целевой») — на стороне клиента: серверного лимита
намеренно нет, аватар в ответе — это метаданные `Image`, а не файл.

## 4. 👁 Правила доступа `GetBreadcrumbs`

Метод отвечает на вопрос «как пройти от меня до этого человека», поэтому доступ
строже, чем у `Get`: путь существует только **вниз**.

| Кого спрашиваем | Ответ |
|---|---|
| Себя (пустой `identifier` или свой id) | цепочка из одного элемента |
| Партнёра из своей команды (любой глубины) | полная цепочка от меня до него |
| Своего спонсора / соседнюю ветку / чужую сеть | `PermissionDenied` |
| Несуществующего id или username | `NotFound` |

Глобальное право просмотра (админ/поддержка) на это правило **не влияет**: оно
даёт видеть чужой профиль, но не создаёт пути к нему. Для целевого вне своей
структуры такой смотрящий получает тот же `PermissionDenied`.

Инвариант, на который можно опираться безусловно: `chain_ids[0]` **всегда** равен
`executor_distributor_id`, `chain_ids[last]` — `view_distributor_id`. Звеньев выше
запрашивающего в цепочке не бывает.

### Ошибки

| Ситуация | Код | Строка |
|---|---|---|
| Целевой вне моей структуры | `PermissionDenied` | `DISTRIBUTOR_VIEW_PERMISSION_DENIED` |
| Целевого не существует | `NotFound` | `DISTRIBUTOR_VIEW_NOT_FOUND` |
| Сессия не привязана к дистрибьютору | `NotFound` | `DISTRIBUTOR_NOT_FOUND` |
| Токен не Session (гость) | `Unauthenticated` | `GUEST_ACCESS_DENIED` |
| Скоуп токена — подтверждение | `PermissionDenied` | `ACCESS_SCOPE_DENIED` |

Гостевого доступа у метода нет намеренно: крошки — это положение относительно
конкретного смотрящего, вне сессии они не определены.

## 5. 🩹 Правка `v0.3.17` — цепочка больше не уходит выше запрашивающего

Только для тех, кто успел посмотреть `v0.3.16` на staging. Поведения, описанного
выше, оно не меняет — оно приводит реализацию к нему.

**Было (`v0.3.16`, ошибка).** Для смотрящего с глобальным правом просмотра, у
которого своей цепочки к целевому нет, метод отдавал вышестоящую линию целевого
до корня сети. Запрос дистрибьютора `406` из-под дистрибьютора `4` (соседняя
ветка) возвращал `chain_ids = [1, 2, 9, 58, 406]` — ни одного звена из структуры
запрашивающего, зато его собственный спонсор `1` в списке.

**Стало (`v0.3.17`).** Такой ответ невозможен: нет пути вниз — `PermissionDenied`.
Ветка «вышестоящая линия для глобального просмотра» убрана целиком.

Отличить старое поведение от нового на клиенте можно было бы по
`chain_ids[0] != executor_distributor_id`, но проверка не нужна — в `v0.3.17`
это условие не выполняется никогда.

## 6. 🧭 `MarketingService.GetSlotBreadcrumbs` — те же крошки, но по слотам (`v0.3.18`)

Аналог `DistributorService.GetBreadcrumbs` для маркетингового дерева: путь от
активного слота запрашивающего вниз до указанного слота.

### `biconom/client/marketing/marketing.proto`

```protobuf
service MarketingService {
    // ... существующие RPC не тронуты ...

    rpc GetSlotBreadcrumbs(biconom.types.Slot.Id) returns (GetSlotBreadcrumbsResponse);
}

message GetSlotBreadcrumbsResponse {
    uint32 executor_slot_id = 1;                     // мой активный слот в дереве целевого
    uint32 view_slot_id = 2;                         // запрошенный слот — хвост цепочки
    uint32 tree_id = 3;                              // дерево, общее для обоих
    repeated uint32 chain_ids = 4;                   // цепочка сверху вниз
    repeated biconom.types.Slot slots = 5;
    repeated biconom.types.Distributor distributors = 6;
    repeated biconom.types.Account accounts = 7;
}
```

Запрос — `biconom.types.Slot.Id` напрямую, как в `GetSlot` / `GetSlotV2`.
Идентификатор **обязателен**: именно он задаёт дерево, а без дерева неизвестно, от
какого слота вести отсчёт.

### Как определяется точка отсчёта

Slot-контекст сессии **не используется** — сессия может быть открыта от слота
другого дерева, и тогда цепочка считалась бы не от того корня. Порядок такой:

1. дерево берётся у запрошенного слота (`view_slot.tree_id`);
2. в этом дереве ищется активный слот авторизованного дистрибьютора;
3. проверяется связь: запрошенный слот — это мой слот или слот в его структуре.

### Как рисовать

`chain_ids` приходит уже в порядке отрисовки, `[0]` — мой слот, последний —
запрошенный. Джойны:

```
chain_ids[i] → Slot.id → Slot.distributor_id → Distributor.id
                                             → Distributor.account_id → Account.id → Account.user
```

| Что показать | Откуда |
|---|---|
| Логин владельца звена | `Distributor.username` |
| Аватар | `Account.user.avatar` |
| Положение звена в дереве | `Slot.relationship_state` (от `executor_slot_id`) |
| Номер ветки, уровень | `Slot.parent_branch_number`, `Slot.level` |

⚠️ **Два разных `relationship_state` в одном ответе.** У `Slot` он про
**маркетинговую** иерархию (от моего слота), у `Distributor` — про
**реферальную** (от меня). Они не обязаны совпадать: слот в моей структуре
дерева может принадлежать кому угодно, и наоборот — личник может стоять в
чужой ветке. Не подписывайте звено словом «команда» по `Distributor`.

Контакты (`email`, `telegram_username`) в этом ответе **не заполняются** — как и
в `SearchSlots`. Если для экрана они нужны — скажите, добавим.

### Ошибки

| Ситуация | Код | Строка |
|---|---|---|
| Запрошенный слот вне моей структуры дерева (вышестоящий, соседняя ветка, чужое дерево) | `PermissionDenied` | `SLOT_VIEW_PERMISSION_DENIED` |
| Идентификатор слота не передан или слота не существует | `NotFound` | `SLOT_VIEW_NOT_FOUND` |
| У меня нет активного слота в этом дереве | `NotFound` | `SLOT_NOT_FOUND` |
| Сессия не привязана к дистрибьютору | `NotFound` | `DISTRIBUTOR_NOT_FOUND` |
| Токен не Session (гость) | `Unauthenticated` | `GUEST_ACCESS_DENIED` |
| Скоуп токена — подтверждение | `PermissionDenied` | `ACCESS_SCOPE_DENIED` |

### Чем отличается от `breadcrumbs` внутри `GetSlot`

`MarketingSlot.breadcrumbs` (V1) — это цепочки по `MARKETING_LEVEL_LIMIT` слотов
с номерами веток, под конкретную визуализацию дерева. `GetSlotBreadcrumbs` отдаёт
плоский линейный список звеньев — под строку навигации. Первое из второго не
выводится и наоборот; методы независимы.

## 7. 👥 `AccountService.GetCurrent` — последние личники в ответе главного экрана (`v0.3.20`)

**Проблема.** Блок «мои последние партнёры» на главной требовал второго вызова —
`ListPartners` с сортировкой и лимитом, — хотя `GetCurrent` и так уже отдаёт
аккаунт, дистрибьюторов, слоты и дивидендный пул одним запросом. Два запроса на
один экран, причём второй нужен ровно ради трёх карточек.

**Решение.** `AccountView` получил встроенный список последних лично
приглашённых — в **корне** ответа, рядом с `accounts` и `distributors`.

### Контракт

```protobuf
message AccountView {
    // ... поля 1–6 не тронуты ...

    // Последние лично приглашённые партнёры аккаунта (первая линия реферального
    // дерева), новые первыми. Количество фиксировано бэкендом — 3.
    repeated biconom.types.Distributor last_partner_distributors = 7;
}
```

`GetCurrentRequest` **не менялся** — новых параметров нет.

> ⚠️ В промежуточной `v0.3.19` этот список лежал внутри элемента `distributors[]`
> под именем `partner_distributors` (поле 8). В `v0.3.20` он переехал в корень и
> сменил имя на `last_partner_distributors`; во вложенном
> `AccountView.Distributor` поле 8 просто удалено. Если клиент успел
> сгенерироваться по `v0.3.19` — нужна перегенерация и правка места чтения.

### Что в списке

| Свойство | Значение |
|---|---|
| Кто попадает | Прямые потомки в реферальном дереве — те, кто зарегистрировался по инвайт-ссылке |
| Сколько | Ровно 3 (меньше, если партнёров меньше). Константа бэкенда |
| Порядок | Новые первыми — последняя регистрация в `[0]` |
| Чей это список | Всего аккаунта. Если аккаунт владеет несколькими дистрибьюторами, их первые линии объединяются и отдаются 3 самые свежие регистрации по всем |
| Под кем стоит партнёр | `last_partner_distributors[].parent_id` — id того дистрибьютора аккаунта, чья это первая линия |
| `relationship_state` | Всегда `{ kind: TEAM, level_diff: 1, branch_number: <порядковый номер партнёра у родителя> }` |

### Аккаунты и профили

Отдельного запроса на карточку не нужно: аккаунты-владельцы партнёров попали в
тот же дедуплицированный справочник `AccountView.accounts`, что и раньше
использовался для исполнителя и вышестоящих.

```
last_partner_distributors[i].account_id → accounts[].id → accounts[].user
```

Внутри `User` доступны `avatar`, `presence_status`, `is_banned`, `created_at` —
всё, что нужно карточке партнёра. Логин берётся из самого
`last_partner_distributors[i].username`.

**Контакты партнёров заполняются.** `email` и `telegram_username` во вложенном
`User` приходят теперь у всех аккаунтов справочника: у собственного, у
вышестоящих из `distributor_upline_visibility_depth` и у личников из
`last_partner_distributors`. Пустые поля означают ровно одно — контакт не
привязан (или Telegram отвязан), а не отсутствие прав. `telegram_user_id`
наружу по-прежнему не отдаётся.

### Совместимость

Для клиента, сгенерированного до `v0.3.19`, ломающих изменений нет: поле новое,
`GetCurrentRequest` не тронут, поведение остальных полей прежнее — просто не
видно `last_partner_distributors`. Клиенту на `v0.3.19` нужна перегенерация
(см. врезку выше). Побочный эффект для всех: `accounts` теперь может содержать
до трёх дополнительных аккаунтов. Если фронт где-то трактовал `accounts` как «я
и мои вышестоящие» — опираться нужно на `executor_account_id` и на join по
конкретным спискам, а не на состав справочника.
