# CHANGELOG: 13 Августа 2026 (proto v0.3.9 + v0.3.10)

Новый модуль — **USDT-стейкинг**. Партнёр вкладывает USDT в депозит, получает 12 выплат
дохода по одной каждые 30 суток, после чего депозит закрывается и возвращает тело.
Каждый прирост тела раздаёт реферальные бонусы вверх по спонсорскому дереву в зависимости
от **ранга** получателя.

Документ рассчитан на фронт-команду: ниже расписаны все сообщения, поля, перечисления и
методы, с семантикой каждого значения.

> ✅ **Не breaking.** Всё добавленное — новые файлы плюс одно новое поле в существующем
> `oneof` и одно новое значение существующего `enum`. Старые клиенты их игнорируют,
> номера прежних полей не тронуты.

**Состав релиза:**

| Версия | Что |
|---|---|
| `v0.3.9` | `types/staking.proto`, `client/staking/staking.proto`, `admin/staking/staking.proto`, поле в `Ledger.Owner` |
| `v0.3.10` | `TOPIC_STAKING_RANK_ACHIEVED` в `notification_preferences` |

## ⚠️ Прочитать до начала вёрстки

**1. Создание депозита необратимо.** Отменить созданный депозит не может ни партнёр, ни
админ: в той же группе проводок деньги уже разошлись реферальной лестницей вверх по
дереву. Нужен экран подтверждения перед `CreateDeposit`.

**2. Двойной тап по кнопке создаёт два депозита.** Блокируйте кнопку до получения ответа.
`CreateDepositRequest` принимает `idempotency_key` — передавайте его, но защиту на
клиенте это не отменяет.

**3. Модуль может быть выключен.** `State.settings.service_status` принимает значения
`ACTIVE` / `PAUSED` / `STOPPED`; при `PAUSED` и `STOPPED` создание депозитов запрещено и
вернёт ошибку. Кнопку покупки надо прятать по этому полю, а не показывать всегда.

**4. Ставки — коэффициенты, а не проценты.** `"0.05"` означает 5%. Для показа умножить
на 100. Подробнее — в соглашениях о величинах ниже.

## 1. 💰 `biconom/types/staking.proto` — модели

Новый файл, всё вложено в `message Staking`.

### Два процента, которые нельзя путать

В модуле две независимые шкалы. Объединить их в одну таблицу нельзя:

| | **Тир** (`Staking.Tier`) | **Ранг** (`Staking.Rank`) |
|---|---|---|
| Что даёт | доход **со своих** денег | долю в раздаче **с чужих** депозитов |
| От чего зависит | сумма активных депозитов **сейчас** | вклад и оборот **за всё время** |
| Динамика | плавает вверх и вниз | **никогда не понижается** |
| Где взять | `Config.tiers`, `DepositsSummary.current_rate` | `Config.ranks`, `RankProgress` |

Партнёр может одновременно иметь ранг 12 (`"0.16"` с чужих депозитов) и тир `"0.05"`
(минимальная ставка со своих), если ранг взят давно командным оборотом, а собственных
активных депозитов сейчас на $100. На экране это две разные сущности.

### Соглашения о величинах

- **Деньги** — строками, как балансы `Ledger`. Не парсить в `double`.
- **Ставки** — тоже строками, но **коэффициентом**: `5%` → `"0.05"`, `16%` → `"0.16"`.
  Умножается на тело напрямую (`выплата = тело × rate`), поэтому ни клиент, ни сервер
  не делят на 100 и не гадают о масштабе. Для показа умножить на 100 и дописать `%`.
- **`optional` означает «значения нет», а не «ноль».** У ранга 1 нет требования по
  обороту, у рангов 1–3 нет бонуса за достижение — это принципиально разные вещи, чем
  «требование ноль». Не подставляйте `0` вместо отсутствия.
- **Время** — `google.protobuf.Timestamp`, отсутствие = поле не заполнено.

### `Deposit` — депозит

Собственный счёт-леджер, собственное расписание, собственные флаги реинвеста.

| Поле | Тип | Семантика |
|---|---|---|
| `id` | `uint32` | |
| `distributor_id` | `uint32` | владелец |
| `ledger_id` | `uint64` | счёт депозита; его баланс **и есть** тело |
| `currency_id` | `uint32` | всегда USDT; **все** денежные поля депозита в ней |
| `initial_amount` | `string` | сумма на момент создания, **не меняется никогда** |
| `body` | `string` | тело: у активного — баланс счёта, у закрытого — снимок на момент закрытия |
| `total_income_paid` | `string` | начислено дохода за всё время, независимо от того, ушёл он на кошелёк или в тело |
| `status` | `Status.Id` | `ACTIVE` / `CLOSED` |
| `source` | `Source.Id` | `MANUAL` / `BODY_REINVEST` |
| `source_deposit_id` | `uint32` | закрытый депозит, тело которого открыло этот; `0` при `MANUAL` |
| `plan_id` | `uint32` | снимок тарифа, сейчас всегда `1` |
| `cycles_total` | `uint32` | снимок, сейчас `12` |
| `cycle_interval_secs` | `uint32` | снимок, сейчас `2592000` (30 суток) |
| `cycles_done` | `uint32` | реализовано выплат, `0..cycles_total` |
| `created_at` | `Timestamp` | точка отсчёта расписания |
| `next_payout_at` | `Timestamp` | **плановый** момент следующей выплаты; пусто у закрытого |
| `last_cycle_at` | `Timestamp` | плановый момент последней выплаты; пусто, если выплат не было |
| `closed_at` | `Timestamp` | пусто, пока активен |
| `updated_at` | `Timestamp` | |
| `reinvest_profit_applied` | `bool` | по нему отработает **ближайшая** выплата |
| `reinvest_profit_requested` | `bool` | что установил партнёр |
| `reinvest_deposit` | `bool` | переоткрыть тело новым депозитом при закрытии |

**Прогресс депозита** для полосы на карточке: `cycles_done / cycles_total`.

**«Сколько ушло в реинвест»** по этому депозиту = `body − initial_amount`. Отдельного
поля намеренно нет — величина выводится из двух имеющихся.

**Два флага реинвеста — разные вещи, не сводите в один переключатель:**

- `reinvest_profit` — доход каждого цикла уходит в тело **этого же** депозита;
- `reinvest_deposit` — при закрытии тело целиком открывает **новый** депозит.

**Отложенное отключение.** Включение реинвеста прибыли действует немедленно, отключение —
после ближайшей выплаты. Поэтому полей два: `applied ≠ requested` означает «заявка на
отключение подана, ближайшая выплата ещё уйдёт в тело». Это надо показывать: иначе
пользователь решит, что переключатель не сработал. Заявку можно отозвать повторным
включением до наступления выплаты.

```
applied = true,  requested = true   → «доход идёт в тело»
applied = true,  requested = false  → «отключится после ближайшей выплаты N-го числа»
applied = false, requested = false  → «доход идёт на кошелёк»
```

### `DepositsSummary` — агрегаты по всем депозитам партнёра

**Не зависят от фильтра списка**: даже когда запрошены только активные депозиты, сводка
считается по всем. Это позволяет экрану «мои депозиты» обойтись одним запросом.

| Поле | Семантика |
|---|---|
| `active_count`, `active_total` | активных сейчас; `active_total` — база выбора тира |
| `current_rate` | ставка тира за цикл, коэффициент строкой; **пустая строка**, если активных депозитов нет |
| `total_count`, `invested_total` | за всё время; `invested_total` — сумма `initial_amount`, то есть реальных внесённых денег |
| `personal_volume` | личный **вклад** для рангов: суммы тел по всем депозитам включая закрытые и включая прирост от реинвеста. Всегда ≥ `invested_total`; разница = объём, созданный реинвестом |
| `total_income_paid` | начислено дохода за всё время |
| `total_reinvested` | сколько из него ушло обратно в тела |

### `Tier` — ступень собственной доходности

`min_active_total` (нижняя граница) + `rate` (коэффициент). Сетка захардкожена, приходит
в `Config.tiers` по возрастанию порога. Ставка **пересчитывается на каждой выплате**: тир
не «достигается» и не фиксируется. Закрылся депозит → сумма упала → следующая выплата по
более низкой ставке.

### `Rank` — ступень карьерной лестницы

| Поле | Семантика |
|---|---|
| `rank` | 1..12 |
| `referral_rate` | доля в реферальной лестнице, коэффициент строкой |
| `required_personal_volume` | требуемый личный вклад |
| `required_team_volume` | `optional` — **отсутствует у ранга 1** |
| `max_per_leg` | `optional` — максимум, который **одна ветка** первой линии даёт в оборот. Отсутствует там же, где и оборот |
| `achievement_bonus` | `optional` — **отсутствует у рангов 1–3** |

**Как работает реферальная лестница.** При каждом приросте тела у кого-то в структуре
вышестоящие получают **разницу** между коэффициентом своего ранга и уже выплаченным вниз,
пока суммарно не наберётся 16%. Пример: прямой спонсор ранга 1 получает 5%, выше него
партнёр ранга 3 получает 7% − 5% = 2%, ещё выше ранг 12 получает 16% − 7% = 9%. Обход
останавливается на 16%; недобранное никуда не идёт.

Отсюда важное для интерфейса: **сумма реферального начисления не равна `referral_rate` от
базы**. Показывать «ваш ранг даёт 16%» рядом с фактическим начислением в 2% —
верный способ получить тикет в поддержку.

**`max_per_leg` — правило трети.** По умолчанию треть от `required_team_volume`,
округлённая **вверх**: три максимальные ветки обязаны покрывать 100% требования, иначе
ранг недостижим даже теоретически. Задан суммой, а не долей, чтобы на разных рангах
можно было задать разные правила.

### `Leg` и `RankProgress` — квалификация

`Leg` отвечает на вопрос «почему не взял ранг» по одной ветке первой линии:

| Поле | Семантика |
|---|---|
| `distributor_id` | лидер ветки |
| `leader_personal_volume` | личный вклад самого лидера |
| `branch_volume` | объём всей ветки: лидер + все нижестоящие |
| `max_per_leg` | лимит для проверяемого ранга |
| `counted` | сколько фактически засчитано |
| `capped` | `true` — сработал лимит, ветка дала бы больше |
| `leader_exceeds_cap` | `true` — засчитан **весь** личный вклад лидера, потому что он превышает лимит; нижестоящие этой ветки не учитываются вовсе |

`RankProgress`:

| Поле | Семантика |
|---|---|
| `current_rank` | `0` — квалификации нет |
| `achieved_at` | пусто при `current_rank == 0` |
| `is_max` | `true` — ранг 12, блок `next` пуст |
| `next` | требования следующего ранга; пусто при `is_max` |
| `personal_volume` | личный вклад; **никогда не уменьшается** |
| `team_volume` | `optional` — **засчитанный** оборот под следующий ранг; пусто при `is_max` |
| `team_volume_uncapped` | полный оборот команды **без** лимитов |
| `legs_count` | число веток первой линии |
| `achievements` | по записи на каждый взятый ранг, с датой и `obligation_id` |
| `legs` | разбивка по веткам — **в `GetState` всегда пусто** |

`team_volume_uncapped − team_volume` — это ровно то, что срезал лимит на ветку, и главный
ответ на «у меня в команде $60 000, почему не дали ранг за $50 000». Показывайте обе
цифры.

`achievements` — готовый экран «карьера»: 12 карточек, на взятых галочка и дата. Ранги
берутся последовательно и никогда не теряются, поэтому список всегда плотный от 1 до
`current_rank`.

### `Obligation` — обязательство по бонусу за ранг

Создаётся **всегда**, когда у достигнутого ранга есть бонус — и при автовыплате, и при
ручной. Даёт единый аудиторский след.

| Поле | Семантика |
|---|---|
| `id`, `distributor_id`, `rank` | |
| `amount` | **снимок** на момент достижения: последующее изменение таблицы рангов уже созданные обязательства не меняет |
| `currency_id` | |
| `created_at` | |
| `released` | `false` — деньги ещё не выплачены, ждёт решения админа |
| `released_at` | пусто, пока `released == false` |
| `released_by_user_id` | `0` — выплачено автоматически |
| `ledger_group_id` | `0` — не выплачено |

Состояний ровно два. **Отказать в бонусе нельзя** — только выплатить, раньше или позже.

### `Event` — журнал

Только **личные** события партнёра по его депозитам. Реферальные бонусы, полученные от
структуры, сюда **не попадают** — они видны в общей истории транзакций кошелька.

Общие поля: `id` (глобальный монотонный, он же курсор), `seq` (номер в рамках партнёра),
`deposit_id` (`0` — событие не привязано к депозиту, это достижение ранга), `ts`,
`ledger_group_id` (`0` — событие без денег).

`ts` — **бизнес-время**: для выплат это плановый момент цикла, а не момент фактической
обработки. После простоя сервиса они расходятся, и в истории стоит плановый.

`oneof data`, шесть видов:

| Вид | Поля |
|---|---|
| `DepositOpened` | `amount`, `source`, `source_deposit_id` |
| `IncomePaid` | `payout_seq`, `amount`, `rate`, `active_deposits_total`, `body_at_payout`, `is_final` |
| `IncomeReinvested` | `payout_seq`, `amount`, `body_after` |
| `AutoReinvestChanged` | `actor` (`USER` / `SYSTEM`), `requested`, `applied` |
| `DepositClosed` | `body`, `reinvested_into_deposit_id` |
| `RankAchieved` | `rank`, `achievement_bonus` (optional), `obligation_id` (optional) |

`IncomePaid` самодостаточен для перепроверки прямо в интерфейсе:
`body_at_payout × rate == amount`, а `active_deposits_total` объясняет, **почему** ставка
именно такая. Это снимает большинство вопросов «почему мне начислили столько».

`AutoReinvestChanged` с `actor = SYSTEM` — это система применила отложенное отключение в
момент выплаты. Событие пишется специально, чтобы партнёр не гадал, почему выплата ушла
в тело.

### `State` — всё состояние одним ответом

| Поле | Семантика |
|---|---|
| `settings` | изменяемые настройки: `service_status`, `min_deposit`, дефолты реинвеста |
| `summary` | `DepositsSummary` по **всем** депозитам |
| `deposits` | новые сверху; закрытые только по флагу запроса |
| `rank` | `RankProgress` **без** `legs` |
| `to_next_tier` | `optional` — сколько не хватает до следующего тира; пусто, если тир максимальный или активных депозитов нет |
| `next_tier_rate` | `optional` — ставка следующего тира |
| `total_referral_received` | получено реферальных бонусов за всё время |
| `total_achievement_bonus_received` | получено бонусов за ранги |
| `obligations` | все бонусы за ранги, включая невыплаченные; максимум 9 записей за всю жизнь аккаунта |

Чего в `State` нет намеренно: таблица рангов и сетка тиров (статичны — берите
`GetConfig` один раз и кэшируйте) и `rank.legs` (не ограничена по размеру).

`settings` лежит именно в состоянии, а не только в `Config`, потому что меняется на лету
и напрямую влияет на экран: по `service_status` решать, показывать ли кнопку покупки, по
`min_deposit` — валидировать форму, по дефолтам — предзаполнить переключатели.

### `ServiceStatus` — глобальный статус модуля

| Значение | Что можно |
|---|---|
| `ACTIVE` | штатная работа |
| `PAUSED` | ручное создание депозитов **запрещено**; выплаты, реинвест прибыли и автоматический реинвест тела при закрытии продолжают работать — это исполнение уже принятых обязательств, а не новая продажа |
| `STOPPED` | всё заморожено; плановые моменты выплат накапливаются и догоняются после возврата в `ACTIVE` |

### `Config`, `Settings`, `RankBonusSetting`, `Summary`

`Config` — `currency_id`, 12 `ranks`, сетка `tiers`, `cycles_total`,
`cycle_interval_secs`, вложенные `settings`. Всё кроме `settings` меняется только
пересборкой сервиса.

`Settings` — `min_deposit`, `default_reinvest_profit`, `default_reinvest_deposit`,
`service_status`. Минимум входа на реинвест прибыли **не действует**: в тело добавляется
любая начисленная сумма, даже меньше минимума.

`RankBonusSetting` — `rank`, `achievement_bonus` (optional, отсутствует у 1–3),
`auto_release`. Админский экран.

`Summary` — админская сводка по модулю: `total_in_deposits`, `deposits_active`,
`deposits_total`, `total_income_paid`, `total_referral_paid`,
`total_achievement_bonus_paid`, `obligations_pending_amount`,
`obligations_pending_count`, `service_status`.

## 2. 🧾 `Ledger.Owner.staking_deposit_id` — новый владелец счёта

```protobuf
message Owner {
    oneof entity {
        uint32 org_pool_id = 1;
        uint32 wallet_id = 2;
        uint32 payment_network_id = 3;
        uint32 exchange_id = 4;
        uint32 staking_deposit_id = 5;   // ← новое
    }
}
```

Каждый депозит владеет **собственным счётом-леджером**: баланс этого счёта **и есть тело**
депозита. Отдельного поля с телом в хранилище нет — двойной учёт исключён по построению.

Флаги счёта — `ALLOW_DEBIT | ALLOW_CREDIT` **без** `ALLOW_NEGATIVE`: счёт депозита это
реальное обязательство перед партнёром, уйти в минус он не может.

Для истории транзакций: проводки стейкинга теперь могут иметь владельцем
`staking_deposit_id`. Если экран истории делает исчерпывающий разбор `oneof entity` —
добавьте ветку, иначе такие записи отрисуются как «неизвестный владелец».

## 3. 📱 `biconom/client/staking/staking.proto` — клиентский сервис

9 методов. Дистрибьютор определяется **контекстом авторизации**, не из запроса: партнёр
видит и меняет только свои депозиты. Чужой или несуществующий депозит одинаково даёт
`NOT_FOUND` — по ответу их не различить.

| RPC | Запрос → ответ | Назначение |
|---|---|---|
| `GetState` | `GetStateRequest` → `State` | всё состояние; главный метод экрана |
| `GetConfig` | `Empty` → `Config` | статичная экономика; забрать один раз и кэшировать |
| `GetDeposit` | `Deposit.Id` → `Deposit` | карточка депозита |
| `CreateDeposit` | `CreateDepositRequest` → `Deposit` | создание |
| `SetAutoReinvestProfit` | `SetAutoReinvestProfitRequest` → `Deposit` | реинвест прибыли |
| `SetReinvestDeposit` | `SetReinvestDepositRequest` → `Deposit` | реинвест тела |
| `ListEvents` | `ListEventsRequest` → `Event.List` | весь журнал |
| `ListDepositEvents` | `ListDepositEventsRequest` → `Event.List` | журнал одного депозита |
| `GetRankProgress` | `Empty` → `RankProgress` | детальный разбор ранга **с `legs`** |

**`GetStateRequest.include_closed_deposits`** — единственный фильтр. `false`/не задано —
только активные. На `summary` не влияет.

**`CreateDepositRequest`**: `amount` (строкой, не меньше `settings.min_deposit`),
`idempotency_key` (см. предупреждение выше), `reinvest_profit` и `reinvest_deposit` —
`optional`: если не задать, применяются дефолты из настроек. Ограничения на количество
активных депозитов **нет**. Запрещено при `PAUSED` и `STOPPED`.

**Пагинация журнала.** `cursor` — `Event.id` последнего полученного события, exclusive;
`null` — с самого нового. `sort` задаёт направление и лимит, по умолчанию `BACKWARD, 50`.
Потолок страницы — 200. **Конец списка определяется тем, что пришло меньше записей, чем
`sort.limit`** — отдельного `next_page_token` в репозитории нет нигде, это общая
конвенция.

**Почему `GetRankProgress` отдельным методом.** Число веток первой линии не ограничено: у
крупного лидера их сотни, и главный экран стал бы самым тяжёлым именно у самых ценных
партнёров. В `GetState` тот же блок `rank` приходит без `legs`.

## 4. 🛠 `biconom/admin/staking/staking.proto` — админский сервис

13 методов под одним правом `ADMIN_STAKING`.

| RPC | Назначение |
|---|---|
| `GetState(distributor_id, include_closed_deposits)` | состояние любого партнёра одним запросом |
| `GetDeposit` | карточка любого депозита |
| `ListEvents(distributor_id, …)` | журнал любого партнёра |
| `ListDepositEvents` | журнал любого депозита |
| `GetRankProgress(distributor_id)` | разбор «почему не взял ранг» — **всегда с `legs`** |
| `GetConfig` | та же конфигурация, что у клиента |
| `GetSummary` | сводка по модулю |
| `ListObligations` | фильтры: `released`, `rank`, `distributor_id`; курсорная пагинация |
| `GetObligation` | карточка обязательства |
| `ReleaseObligation` | **выпустить деньги** по одному обязательству |
| `ListRankBonusSettings` | автовыплата по каждому рангу |
| `SetRankBonusAutoRelease(rank, auto_release)` | переключить автовыплату |
| `UpdateSettings` | минимум входа, дефолты реинвеста, статус приёма |

`ReleaseObligation` необратим и создаёт проводку. Повтор по уже выплаченному
обязательству — ошибка, а не no-op: админ должен увидеть, что деньги уже ушли.

`SetRankBonusAutoRelease` действует **только на будущие достижения** — уже созданные
обязательства не трогает.

`UpdateSettings` — частичное обновление: применяются только переданные поля.

Потолок админской страницы — 200 записей, по умолчанию 50.

## 5. 🔔 `TOPIC_STAKING_RANK_ACHIEVED` — новый топик уведомлений (v0.3.10)

```protobuf
enum Topic {
    // …
    TOPIC_BONUS_RECEIVED = 20;
    TOPIC_STAKING_RANK_ACHIEVED = 21;   // ← новое
}
```

**Зачем отдельный топик, а не ветка `TOPIC_BONUS_RECEIVED`.** Частоты отличаются на два
порядка: доход по депозиту — 12 уведомлений на каждый депозит, достижение ранга —
максимум 12 **за всю жизнь аккаунта**. Один переключатель на оба события заставлял бы
партнёра выбирать между «шумом каждый месяц» и «пропустить редкое важное событие».

**Доставка — только Telegram**, `optional`, включён по умолчанию. Email и push для этого
топика запрещены политикой: событие редкое и наградное, ему не нужен ни push на все
устройства, ни письмо. В экране настроек уведомлений у этого топика должен быть **один**
переключатель, не три.

**Текст условный.** О сумме бонуса уведомление говорит только тогда, когда бонус уже
выплачен. В ручном режиме деньги приходят позже отдельным `TOPIC_BONUS_RECEIVED` —
обещать их в уведомлении о ранге нельзя.

### Что попадает в `TOPIC_BONUS_RECEIVED`

Это umbrella-топик; конкретный вид начисления различается полем `kind` в payload'е.
Стейкинг добавляет три значения:

| `kind` | Когда |
|---|---|
| `staking_income` | доход по депозиту за цикл — 12 раз на депозит |
| `staking_referral` | доля реферальной лестницы с чужого депозита; в тексте указаны логин источника, глубина и **фактическая ставка** (разница процентов, по которой посчитана сумма) |
| `staking_rank_premium` | бонус за ранг, выплаченный админом вручную |

Отдельный топик под реферальные начисления не заводился: через `bonus_received` уже идут
matching / marketing / structure такой же частоты, и переключатель у партнёра всё равно
один — «бонусные начисления».
