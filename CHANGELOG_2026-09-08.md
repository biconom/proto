# CHANGELOG: 8 Сентября 2026 (proto `v0.3.23` → `v0.3.24`)

Стейкинг: у депозита появилась **блокировка маркетинга** и признак **подарка от
компании**, а у админа — два метода под `ROOT`: подарить депозит и переключить
блокировку у любого депозита.

Суть механики. Реферальная лестница стейкинга платит аплайну **с прироста тела**
депозита — при его создании и при реинвесте прибыли в тело, и тот же прирост
идёт в объёмы для рангов. Депозит с `marketing_blocked = true` **вне
маркетинга**: он не порождает ни долей лестницы, ни токенов упущенной выгоды и
не входит в личный вклад, объём ветки и командный объём. Всё остальное у такого
депозита штатное — доходность самому партнёру и тир (тело входит в сумму
активных). У одного партнёра могут быть оба вида депозитов одновременно: свой
работает как раньше, подарочный — нет.

> ✅ **Не breaking.** Добавлены поля в конец существующих сообщений, значение в
> конец enum, два новых события журнала и два новых RPC в админский сервис.
> Старые клиенты новые поля игнорируют, wire-формат прежних не тронут.

## Что нужно сделать фронту — коротко

| Действие | Где подробно |
|---|---|
| Перегенерировать клиент из `.proto` | — |
| В карточке депозита показать бейдж «подарок» по `granted_by_admin` / `source == ADMIN_GRANT` | §1 |

## 1. 🏷 `Staking.Deposit` — два новых поля и новое значение `Source`

### `biconom/types/staking.proto`

```protobuf
message Deposit {
    // ... поля 1–22 без изменений ...

    // true — прирост тела НЕ раздаётся вверх по реферальной лестнице.
    bool marketing_blocked = 23;   // ← новое
    // true — создан админом от имени компании (GrantDeposit).
    bool granted_by_admin  = 24;   // ← новое

    message Source {
        enum Id {
            UNSPECIFIED   = 0;
            MANUAL        = 1;
            BODY_REINVEST = 2;
            ADMIN_GRANT   = 3;     // ← новое
        }
    }
}
```

| Поле | Кто задаёт | Меняется ли |
|---|---|---|
| `marketing_blocked` | `GrantDeposit` при создании, потом `SetDepositMarketingBlock` | да, в любом статусе депозита; объёмы пересчитываются сразу |
| `granted_by_admin` | только `GrantDeposit` | нет, один раз при создании |

Поля независимы: подарок может быть **с** лестницей (`granted_by_admin = true`,
`marketing_blocked = false`), а обычный депозит партнёра — заблокирован админом.

`source == ADMIN_GRANT` и `granted_by_admin == true` — одно и то же, выражено
дважды ради фильтров и отчётов. У депозита, открытого реинвестом тела подарка,
`source == BODY_REINVEST` и `granted_by_admin == false`: подарком был исходный
депозит, а не порождённый. **Блокировка при этом наследуется** — иначе цепочка
«созрел → реинвест» превращала бы подарок в полноценную лестницу от всего тела.

### Что показать партнёру

- `granted_by_admin` — бейдж «подарок от компании».
- `marketing_blocked` — пометка «депозит вне маркетинга». Показывать нужно:
  партнёр иначе не поймёт, почему спонсор ничего не получил, в журнале спонсора
  нет `referral_received`, а `DepositsSummary.personal_volume` меньше
  `invested_total`.

## 2. 📒 Два новых события журнала `Staking.Event`

```protobuf
message Event {
    message MarketingBlockChanged {
        bool marketing_blocked = 1;   // новое значение Deposit.marketing_blocked
    }
    message DepositGranted {
        string amount = 1;
        bool marketing_blocked = 2;   // с каким значением подарок создан
    }
    oneof data {
        // ... 10–18 без изменений ...
        MarketingBlockChanged marketing_block_changed = 19;   // ← новое
        DepositGranted        deposit_granted         = 20;   // ← новое
    }
}
```

| Событие | Деньги | `ledger_group_id` | Когда |
|---|---|---|---|
| `deposit_granted` | да | группа **подарка**: орг-пул → кошелёк партнёра | `GrantDeposit`, рядом с обычным `deposit_opened` |
| `marketing_block_changed` | нет | `0` | `SetDepositMarketingBlock` с реальной сменой значения |

### Почему подарок — это ДВА события, а не `deposit_opened` с флагом

`GrantDeposit` создаёт **две группы проводок**: подарок (пул → кошелёк) и
покупку депозита (кошелёк → счёт депозита). У каждой денежной группы обязано
быть своё событие со своим `ledger_group_id` — по нему строится список
финансовых транзакций стейкинга (`ListTransactions`). `deposit_opened` уже несёт
группу покупки, поэтому группа подарка получила собственное событие. В ленте
партнёра они стоят рядом с одинаковым `ts`.

`deposit_opened.source` у подарка при этом равен `ADMIN_GRANT` — по нему лента
отличает подарок от покупки без второго события.

`marketing_block_changed` пишется **только при фактической смене** значения:
повторный вызов с тем же значением события не создаёт.

## 3. 🎁 `StakingAdminService.GrantDeposit` — подарить депозит (ROOT)

### `biconom/admin/staking/staking.proto`

```protobuf
rpc GrantDeposit(GrantDepositRequest) returns (biconom.types.Staking.Deposit);

message GrantDepositRequest {
    uint32 distributor_id   = 1;
    string amount           = 2;   // USDT строкой, > 0; минимум модуля НЕ применяется
    bool   marketing_blocked = 3;  // блокировать ли лестницу с этого депозита
}
```

Ответ — карточка созданного депозита, как у клиентского `CreateDeposit`.

### Что делает сервер

1. Группа 1: `amount` на USDT-кошелёк партнёра через платёжную сеть «касса» —
   тем же путём, что `WalletCurrencyService.Gift`. В истории кошелька это
   карточка `gift` с комментарием «Подарочный депозит стейкинга».
2. Группа 2: обычная покупка депозита с кошелька на ту же сумму — та же
   карточка «вложение», что при ручном депозите.
3. Депозит открывается с `granted_by_admin = true`, `marketing_blocked` из
   запроса, реинвест прибыли — из настроек модуля (`default_reinvest_profit`),
   как у ручного.
4. Лестница при создании и объёмы для рангов — только при
   `marketing_blocked = false`.

Кошелёк партнёра в итоге не меняется: деньги прошли через него транзитом и
осели в теле депозита.

### Чего сервер НЕ проверяет

| Ограничение | Применяется |
|---|---|
| Минимальная сумма (`Settings.min_deposit`) | ❌ |
| Персональный `BLOCK_STAKING` партнёра | ❌ |
| Статус модуля `PAUSED` | ❌ |
| Сумма > 0 | ✅ |

Это действие компании, а не продажа: ограничения покупки к нему не относятся.
Уведомление партнёру о подарке **не отправляется** — отдельного шаблона нет,
партнёр увидит депозит в списке и бонус в истории кошелька.

## 4. 🔀 `StakingAdminService.SetDepositMarketingBlock` — переключить блокировку (ROOT)

```protobuf
rpc SetDepositMarketingBlock(SetDepositMarketingBlockRequest) returns (biconom.types.Staking.Deposit);

message SetDepositMarketingBlockRequest {
    uint32 deposit_id       = 1;
    bool   marketing_blocked = 2;  // новое значение Deposit.marketing_blocked
}
```

Один метод на установку и снятие — значение в запросе. Работает при **любом**
статусе депозита, включая созревший и закрытый: у созревшего флаг решает, будет
ли лестница у депозита, открытого реинвестом тела.

Лестница: уже выплаченные доли аплайну не отзываются, новых начислений после
блокировки нет. Объёмы для рангов **пересчитываются сразу**: вклад депозита
(его тело — начальная сумма плюс реинвесты прибыли; у закрытого — тело на
момент закрытия) снимается с личного вклада партнёра и объёма ветки всех его
предков при блокировке и возвращается при снятии. Снятие запускает пересчёт
рангов вверх, и кто-то может взять ранг. **Ранг никогда не понижается**:
достигнутый сохраняется, даже если объёма под него больше нет.

Следствие для экрана партнёра: `DepositsSummary.personal_volume` после
блокировки может уменьшиться — единственный случай, когда эта величина падает.

Повтор с тем же значением — успешный no-op: ответ прежняя карточка, события
нет, объёмы не двигаются.

## 5. 🚦 Ошибки

| Метод | Ситуация | Код |
|---|---|---|
| оба | нет `ROOT` | `PermissionDenied` |
| `GrantDeposit` | `distributor_id == 0` или партнёр не найден | `NotFound` / `InvalidArgument`, `DISTRIBUTOR_NOT_FOUND` |
| `GrantDeposit` | `amount` не число или `0` | `InvalidArgument`, `STAKING_AMOUNT_INVALID` |
| `SetDepositMarketingBlock` | депозит не найден | `NotFound`, `STAKING_DEPOSIT_NOT_FOUND` |

`ADMIN_STAKING` для этих двух методов **недостаточно** — только `ROOT`. Остальные
методы сервиса права не меняли.
