# CHANGELOG: 4 Августа 2026 (proto v0.3.8)

Одно изменение, полностью аддитивное: карточка дистрибьютора теперь может отдавать
его **вышестоящего (спонсора)** — аккаунт и дистрибьютора — в одном ответе.

> ✅ **Не breaking.** Добавлено новое поле №9 в существующее сообщение. Старые
> клиенты его игнорируют, wire-формат прежних полей не тронут. Обновляться можно
> в любой момент после релиза бэкенда.

---

## 1. 👤 Вышестоящий в `DistributorService.Get` — без второго запроса

Раньше, чтобы показать «кто пригласил этого дистрибьютора», фронт видел только
`distributor.parent_id` и был вынужден делать второй `Get` по этому id — то есть
удваивать запрос ради одной строки в карточке. Теперь вышестоящий приходит сразу.

### `biconom/client/distributor/distributor.proto`

```protobuf
message Response {
    // Вышестоящий дистрибьютор (спонсор) — разрешённая ссылка distributor.parent_id.
    message Parent {
        biconom.types.Account account = 1;
        biconom.types.Distributor distributor = 2;
    }

    biconom.types.Account account = 1;
    biconom.types.Distributor distributor = 2;
    // ... поля 3–8 без изменений ...

    // Вышестоящий запрошенного дистрибьютора. Всегда, когда он есть.
    optional Parent parent = 9;   // ← новое
}
```

### Почему вложенная модель, а не два плоских поля

Рассматривался вариант `optional Account parent_account` + `optional Distributor
parent_distributor` двумя отдельными полями верхнего уровня. Выбрана вложенная
модель по трём причинам:

| | Вложенная `Parent` | Два плоских поля |
|---|---|---|
| Признак «вышестоящий есть» | **один** — `parent` присутствует или нет | два независимых `optional`, клиент разбирает 4 состояния вместо 2 |
| Инвариант «аккаунт и дистрибьютор всегда вместе» | гарантирован структурой | держится только на договорённости |
| Расширение (слоты вышестоящего, relationship, состояние) | добавляется внутрь `Parent` | плодит `parent_*` на верхнем уровне |

Плюс это уже принятый в схеме приём: `GetStructureOverviewResponse` тоже держит
вложенные `Group` / `LevelGroup`.

### Именование

Поле названо `parent`, а не `sponsor`, для единообразия со схемой: связь, которую
оно разыменовывает, во всей схеме называется `parent_id` («ID вышестоящего
дистрибьютора» — `types/distributor.proto`), а в `ListResponse` соседствует с
`upline_ids`. Клиенту достаточно увидеть `parent`, чтобы понять, что это
разрешённый `distributor.parent_id`, без изучения синонимов.

### Права видимости

**На этот блок права видимости не распространяются**: доступ уже проверен для
самого запрошенного дистрибьютора. Если карточку отдали — вышестоящий в ней есть.
`account` и `distributor` внутри `Parent` заполняются полноценно, теми же моделями,
что и на верхнем уровне ответа.

### Когда поле пустое

Единственный случай — дистрибьютор является корнем сети (`distributor.parent_id
== 0`). Тогда блок «Пригласил» просто не отображается.

## Совместимость

| | |
|---|---|
| Номера и типы существующих полей | не изменены |
| Новые поля | `Response.parent` (№9) + вложенное `Response.Parent` |
| Старый клиент против нового бэкенда | работает, новое поле игнорируется |
| Новый клиент против старого бэкенда | работает, `parent` всегда пустой |
