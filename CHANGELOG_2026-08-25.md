## 1. ⚠️ `trade_win_usdt` — считается только покупка, значение сменило знак

**Что было.** График принимал в расчёт **оба направления** обмена по паре
`WIN-USDT` и складывал их как бухгалтерское сальдо (`дебет − кредит`). При
`currency_id` = USDT покупка токена — это списание с кошелька, то есть кредит,
и вклад в значение получался **отрицательным**.

Продаж токена в системе не происходило вовсе, поэтому вычитать сальдо было не из
чего: график отдавал отрицательное число за **каждый** период на всём горизонте
данных. Порядок величины — минус миллион с лишним USDT суммарно.

**Что стало.** Считается ровно одно направление — покупка токена за USDT:

| `currency_id` | Что попадает в значение | Смысл |
|---|---|---|
| USDT (котируемая) | нога «отдали USDT» | сколько USDT потрачено на покупку токена |
| WINZU (базовая) | нога «получили WINZU» | сколько токена куплено |

Продажа токена (обратное направление той же пары) в график больше не входит.
Комиссии сделки не учитывались и не учитываются.

### Влияние на клиент

| Вариант вызова | Было | Стало |
|---|---|---|
| `currency_id` = USDT | отрицательное число | то же по модулю, но **положительное** |
| `currency_id` = WINZU | положительное число | **не изменилось**, ни на единицу |

Вариант с WINZU численно идентичен прежнему: все его проводки были дебетовыми,
и сальдо совпадало с суммой. Трогать его не нужно.

Вариант с USDT — единственное место, где нужна проверка. Если экран
компенсировал минус (инверсией, `Math.abs`, `* -1`, «расход» вместо «доход») —
компенсацию надо **снять**, иначе знак перевернётся второй раз.

## 2. 📈 `staking_deposits` — приток денег в стейкинг

Новый монетарный график. Показывает, сколько денег ушло с кошельков партнёров в
**тела депозитов** стейкинга.

### Запрос

```
GetChartRequest {
  chart_name:      "staking_deposits"
  currency_id:     <id USDT — валюта программы>
  scope:           ScopeOptions { ... }        // см. §4
  interval:        Interval { id, timezone_id }
  timestamp_start / timestamp_end
  custom_id:       <опционально>
}
```

Ответ — обычный `biconom.types.Chart` с `monetary_data`: свечи
`timestamp_start` / `timestamp_end` / `value`, где `value` — строка в масштабе
валюты. Никаких новых сообщений.

`currency_id` обязателен, как у любого монетарного графика. Валюта программы —
USDT; другой `currency_id` ошибки не даёт, но вернёт нули.

### Что попадает в значение

Все три способа пополнить тело депозита:

| Событие | Входит |
|---|---|
| Открытие депозита партнёром | ✅ |
| Реинвест **тела** созревшего депозита (открытие нового на всю сумму) | ✅ |
| Реинвест **прибыли** цикла (доход уходит обратно в тело) | ✅ |
| Возврат тела на кошелёк (`ClaimDeposit`) | ❌ движение в обратную сторону |
| Начисленный доход, реферальные бонусы, бонусы за ранг | ❌ это доход, он в графике `income` |

### ⚠️ Это ВАЛОВОЙ приток, а не «привлечено новых средств»

Оба вида реинвеста — повторное вложение денег, которые график уже посчитал
раньше. Партнёр, который вложил $1000, дождался созревания и реинвестировал
тело, даст в сумме $2000, хотя новых денег не принёс.

Так же эти деньги считает и сам модуль стейкинга (личный вклад партнёра растёт
на полную сумму реинвеста), поэтому график и экран стейкинга сходятся между
собой. Но подписывать его на дашборде нужно как **оборот программы**, а не как
приток новых средств — иначе цифра будет читаться неверно.

Если понадобится срез «только новые деньги, без реинвестов» — это отдельный
`chart_name`, скажите, добавим.

### Соотношение с графиком `income`

Пересечения нет и быть не может: `staking_deposits` считает деньги, **уходящие**
с кошелька в депозит, `income` — бонусные начисления, **приходящие** на кошелёк
(включая доход по стейкингу, реферальные доли лестницы и бонусы за ранг). Одна и
та же проводка в оба графика попасть не может.

Нюанс на будущее: когда включён автореинвест прибыли, доход цикла зачисляется на
кошелёк и тут же уходит обратно в тело. Такой цикл даст `+X` в `income` и `+X` в
`staking_deposits` — это не двойной счёт, а два разных факта: доход начислен и
доход вложен.

## 3. 🔐 `GetCharts` требует `ANALYTICS_VIEW`

**Было.** Одиночный `GetChart` требовал `ANALYTICS_VIEW`, а пакетный `GetCharts`
— только `PROFILE_VIEW`. Пользователь, которому отказывали в `GetChart`, те же
самые данные спокойно получал через пакетный вызов.

**Стало.** Все три метода сервиса требуют одно право:

| RPC | Право |
|---|---|
| `GetChart` | `ANALYTICS_VIEW` |
| `GetCharts` | `ANALYTICS_VIEW` ← изменилось |
| `GetSummary` | `ANALYTICS_VIEW` |

**Регрессии для обычных пользователей нет:** `ANALYTICS_VIEW` входит в набор прав
по умолчанию, который получает каждый. Отказ увидит только тот, у кого право
сняли намеренно, — а это и есть желаемое поведение.

## 4. 🧭 Справочник областей видимости

Действует одинаково для `staking_deposits`, `income`, `license_purchases` и
`trade_win_usdt`.

| Что нужно показать | `scope` |
|---|---|
| Только свои данные | `{ id: PERSONAL }` |
| Первая линия, без себя | `{ id: TEAM, team_depth_limit: 1, include_personal: false }` |
| Первая линия + свои | `{ id: TEAM, team_depth_limit: 1, include_personal: true }` |
| Вся команда на любую глубину, без себя | `{ id: TEAM, include_personal: false }` |
| Вся команда + свои | `{ id: TEAM, include_personal: true }` |
| Вся компания | `{ id: COMPANY_WIDE }` |

Отдельного значения enum под «первую линию» нет и не требуется — это `TEAM` с
глубиной 1.

**Поведение по краям:**

- `team_depth_limit` не задан — берётся вся реальная глубина структуры.
  Запросить больше, чем есть, безопасно.
- `team_depth_limit: 0` со `include_personal: false` вернёт **пустой** график, а
  с `include_personal: true` — то же самое, что `PERSONAL`.
- `include_personal` на `COMPANY_WIDE` не влияет.
- `TEAM` считается по **реферальному** дереву — тому же, по которому стейкинг
  платит реферальную лестницу.
- Окно запроса ограничено **366 днями**; шире — `FailedPrecondition`
  `ANALYTICS_TIME_RANGE_LIMIT`.

### Права на `COMPANY_WIDE`

`COMPANY_WIDE` требует **двух** прав одновременно: `ANALYTICS_VIEW` на вход в
метод плюс `ANALYTICS_COMPANY_VIEW` на саму область. Второе выдаётся точечно и
у обычного пользователя его нет — он получит `PermissionDenied`
`PERMISSION_NOT_ALLOWED`.

Личный, первой линии и командный режимы отдельного права не требуют:
`ANALYTICS_VIEW` покрывает все три.
